# 一次真实会话里跑出来的流程（2026-11-17 → 11-18）

> **这一份是观察记录，不是规范。** 规范在 `SKILL.md` 与 `references/`。
> 它的用途：说明 0.8.x 的三份 references 与两个 gate 模式**是从哪条真实故障长出来的**。
>
> **重要：观察对象是一个具体项目（DSJY 记忆库），不是所有项目。**
> 下面凡是「机制」的，换项目也成立；凡是「形态」的，只属于这个项目，抄走会出事。
> 0.8.0 犯的错正是把形态当规范，0.8.1 修的就是这一条。

---

## 0 一句话先说清

```
机制（可迁移）：立项即标准 · 域是推出来的 · 每条规则指回一句话 · 不打补丁 · 绿不算通过
形态（不可迁移）：九个域 · 七段 · 九段任务书 · 四列切片表 · 前缀表 CX/MT/IV… · F1–F8
```

**同一个案例，可以抄出机制，也可以抄出形态。差别是：抄形态的人拿到的是一次推导的下标，不是推导。**

## 1 实际发生的六个阶段（现象层）

| 段 | 用户要什么 | 实际做了什么 | 收口靠什么 |
|---|---|---|---|
| **P0 对矛盾** | 「找三维节点的描述文档」「这三个基本正确，要综合重新来看」「再看看还有没有矛盾的说法，全部看一遍」×5 | 全仓扫 md，逐条比「维 / 跳 / 源头」的说法 | **没用**：口径写在回答里，下一轮又变 |
| **P1 认知重建** | 「回到原来的立项即标准，把记忆系统的哲学全部摘出来」 | 交分析稿 → 被驳回「不要写这种东西，有个屁用」 | 用户自己写条文，AI 只许「对齐 / 补充 / 指出矛盾」 |
| **P2 范畴与立项** | 「要先明确范畴，包括数学范畴，工程范畴」「要写立项书作为总索引总揽」 | 域目录、范畴表、文档纪律、Rust/TS 选型判据 | 立项书 + 文档纪律 + 前缀表 |
| **P3 形式化** | 「先把形式化证明做一下……你写好方式，开始让子代理逐条去证明」 | 4 个子代理并行写 Lean 文件 | 每个子代理交「编译退出码 + sorry 计数 + 定理数」 |
| **P4 工程切片** | 「先开发一个功能，逐个功能来实现」（同一段话重复 12 次） | F1–F8 八片，每片 core + api 两个子代理 | 语义编号 + 测试 + 反证 + 开发日志 |
| **P5 重构** | 「按原本的依赖流程，逐个展开（递归进去规划设计）去做重构」 | R1–R6：区间语义归一、投影归一、删壳、文档对账、拆模块 | 测试条数不变 + 对账脚本退出码 0 |

**P0 是唯一一段跑了两小时还在原地的一步。** 它不是「做得不好」，是**没有产物可以收口**：
矛盾只存在于回答里，下一轮重新讨论就又活了。

## 2 六条**机制**（可迁移 —— 这一节才是重点）

### 2.1 用户的指令是「形态 + 判据」，不是「任务」

```
不要写这种东西，有个屁用。
记忆库系统：
1.此系统由高阶超图驱动。这个系统必须是超图。
…
7.{} 内有序，顺序即时间。[] 是节点，{} 是超边；超边可作成员进入另一个超边，所以超边=节点。
```

用户给的是**编号条文**；AI 交的是**分节分析稿**。**被驳回的不是内容，是形态。**

⇒ 机制：**同一种要求，用户的表达形态就是交付形态的要求。** 他在写条文，你就不许交散文。
（`r5-axiom-chain.md` §5 Q4）

### 2.2 认知靠「指回上一条」验，不靠「听起来对」

```
AI（早期）：要做去重。
用户：去重是错误描述，是因为（超边=节点）。已有节点的情况下，只建超边集。
      不需要去重……没有这层认知，皆是做出来的又是四不像的东西。
```

⇒ 机制：**每条工程规则都要能指回一句前提**；指不回 = 四不像的零件。（C10 / `r5` §3）

### 2.3 矛盾必须逐行裁决，不许「综合」

```
你不要去对代码，对旧的，和新的设计稿，总稿 总稿，立项书等等。去看。
是不是这么一回事。以我当前的话为基准，将矛盾的原话全部拉出来逐行比对。
```

「综合」在用户的语汇里是**和稀泥**：两句话都留着、各自都「对」，于是下游永远两套说法。

⇒ 机制：**冲突不许被表述为「综合」，必须裁决出哪一句作废，并说明依据哪条前提。**（`r5` §5 Q3）

### 2.4 立项是「能被逐行比对的那一份」

⇒ 机制（**不是「必须七段」**）：**下游每篇都要能被立项判「是 / 否」。** 判不了，它就不是基准，是介绍。

**怎么判？** 这一点是我在 0.8.0 搞错的地方：我把它判成了「有没有七段/九域」。
正确的判法是**结构**：表填满了没 / 声明的文档是否存在 / 有没有边界 / 有没有未知项且写了怎么验 / 有没有补丁段。
—— 这五条与项目词汇无关，任何项目都能过或该过。（`r6` §7）

### 2.5 域是「推」出来的

```
用户：域其实指的就是范畴，也就是说用户要开发的这个功能，立项后具备几个域，
      需要几个东西才能解决，逐步去推，去明确边界的同时，引导用户将要求说出来，
      如果用户不明确就得清楚知道行业是怎么做的，不打补丁的方式去落实文档。
```

⇒ 机制：**域的数量由问题推出，不由模板给出。**
推导顺序不许换：推 → 划界 → 引导 → 兜底（行业）→ 落实（不打补丁）。

**这个项目推出来是九个，那是这次推导的结果。** 换个项目可能是三个、五个、十四个。
把「九」写成规范，等于把一次推导的下标当成推导本身。（`r6` §2、§4、§5）

### 2.6 派活靠「把自由度削到只剩实现」，不靠「你去做 F2」

会话里 30 份任务书形态高度一致，成功的那几次都能指出六件齐：
**写域 / 冻结契约 / 语义编号 / 反证 / 报告形态 / 依赖**。

⇒ 机制：**六件不可省，段数随项目增减。** 九段是那次 Rust 项目的形态。（`r7` §3）

### 2.7 验收不靠报告，靠「反证 + 独立探针 + 对账脚本」

会话里出现过三次「全绿但不对」：

| 症状 | 真相 |
|---|---|
| 子代理报 `0 处要改` | 它把 12 条语义写成测试压上去，全绿 —— 这**是**有效结论，因为它同时报告了注入三处都红 |
| 报 `272 passed`，实际基线 `276` | 差 4 条是 lead 自己建的验收探针；对上了才发现是口径差 |
| 文档说 77 个 pub，代码 104 个 | 靠人读判断不了，靠双向对账脚本，退出码 0 才算对齐 |

⇒ 机制：**判据必须能测出红；验收必须有独立于执行者的探针。**（G8 / `r7` §4、§6）

## 3 这个项目里**只属于它自己**的东西（抄走会出事）

| 形态 | 为什么不能抄 |
|---|---|
| 九个域的清单（认知范畴 / 架构 / 形式化 / 工程架构 / 框架 / 细则 / 数据流 / 消费者 / 判据） | 是那次推导的结果；换项目数量与切法都变 |
| 七段立项 / 九段任务书 / 四列切片表 | 是那次的表格样式 |
| 前缀表 `CX MT IV LG AR T OP EA MD FM ER TS DF WP RP AP EC CS CI EE LN UT ST NM UV RD` | 是这个项目的编号系统 |
| 文档纪律那条「前缀永不给别的域」 | 是它的编号约束，不是通识 |
| F1–F8 / R1–R6 的切分 | 是这个项目的功能边界 |
| `00-立项书-0.0.3.md`、`15-实施切片.md` 这类命名 | 是它的编号习惯（gate 只把它当成「名字里含关键词」的一种，不是必须） |

**⇒ 这六行的存在，就是 0.8.1 的全部理由。**

## 4 用户重复最多次的一段话（它本身就是「切片协议」）

同一段指令，在 P4/P5 里出现 **12 次**，一字不差：

```
要根据架构，先开发一个功能，逐个功能来实现，你来负责规划本次任务，明确要实现什么，
怎么连接，怎么写架构 文件夹位置，查验规范标准，而不是用cli测试所谓的通过算通过，
而是代码和功能必须要通过，数据流和信息流要看。因此你要从实现目标开始明确，
数据流和信息流怎么走，这个流程要如何在工程上被程序执行，这个任务再分发给子智能体，
最后由你明确它们的任务的同时，验收它们的任务，检查是否与语义属实，而不是套壳或者查表，
再或者瞎搞瞎写的代码。完成后继续写一份开发日志。
```

七件事：`① 依架构 ② 一次一片 ③ lead 规划 ④ 数据流+信息流都要看 ⑤ 不信 cli 绿 ⑥ 派给子代理并验收语义 ⑦ 开发日志`

**它被重复 12 次，说明 AI 每次都漏掉其中一两件。** 这是 `r7` 存在的直接原因：
**用户不得不手打的东西，应该变成 skill 的默认产出。**

## 5 这段流程暴露的缺陷（对应改动）

| 缺陷 | 会话里的证据 | 改法 |
|---|---|---|
| **认知：抄结论不抄前提** | 「没有这层认知，皆是四不像」 | `r5` + C10/C11 |
| **立项：域被当成清单** | 「域就是范畴，需要几个东西才能解决，逐步去推」 | `r6` 重写为五步推导 + C13 |
| **立项：判据写成形态** | 0.8.0 的 gate grep「九域/串并汇」 | gate 只查结构 + C14 + verify 第 11 节 |
| **交付：绿 ≠ 完成** | 「而不是用 cli 测试所谓的通过算通过」 | `r7` + G8 + `--board` |

## 6 还可以再补的三处（0.8.2 候选）

**按会话里实际浪费掉的时间排序**：

1. **P0 没有产物**。「再看看还有没有矛盾的说法，全部扫一遍」跑了 5 遍。
   缺一份**冲突裁决表**（原话 A / 原话 B / 出处 / 哪句作废 / 依据哪条前提 / 下游要改哪几处），
   以及一个 `--conflicts` 模式：扫 docs 里同一概念的多种说法，要求每个冲突都有裁决行。
   —— 注意：裁决表的**列**是形态，**「每个冲突都必须有裁决」**才是机制。
2. **子代理失败没有兜底**。会话里 `agent-1`–`agent-4` 四个后台子代理**全部失败且没留收尾消息**。
   缺一条：派活前先跑最小探针（能编译 / 能读文件 / 能写文件），失败要么重派要么降级 lead 自写。
3. **换模型导致口径漂移**。会话中模型被换 3 次，每次切换后都要重新对齐条文。
   缺一条：切换后第一件事是重读「唯一权威表」，不是继续干活。

## 7 一句话

> **用户不是没讲清，是他讲清的那一版被反复转述成了另一版。**
> **而转述的两种方式都很便宜：要么抄他的结论，要么抄他的表格。**
> **机制留在原话后面，形态只留在那个项目里。**
