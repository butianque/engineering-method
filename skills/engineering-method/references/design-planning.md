# 第 3 段 · 规划：把「我想做」变成形状

> 合并自原 `system-design-coach`。
> **本段的位置**：第 2 段（递归）与第 2.5 段（检索）之后，第 4 段（冻结判据）之前。
> **没有形状就别冻结判据** —— 那会冻结一个错误的目标。

---

## 1 这段解决什么

用户常直接说「帮我写个 X」，然后卡住：不知拆几个模块、前后端谁调谁、数据存哪、什么先做。

**问题不在写代码，在没先把「形状」画出来。**

产出固定是 **五张图 + 一份任务切片**。不给文章、不给建议清单，给能开工的东西。

---

## 2 先接住，再拆

用户描述里通常混着三个层次：

| 用户说的 | 实际在问 |
|---|---|
| 「我要一个记忆系统」 | **产品目标** |
| 「用什么数据库」 | **技术选型**，而且往往不是真问题 |
| 「我不知道该怎么规划」 | **缺一个形状** —— 真问题 |

**规则**：先问「这个系统给谁用、多久用一次、坏了会怎样」，**不要直接进技术选型**。
选型是形状确定后自然掉出来的结果，反过来做一定返工。

---

## 3 五张图（按顺序画，不能跳）

### 图 1：使用场景（一句话 + 三个数字）

```
谁：______  做什么：______
频率：___ 次/天   数据量：___ 条/年   能容忍挂多久：___
```

**为什么先画**：这三个数字决定后面 90% 的选择。
- 1 次/天 + 1 万条/年 ⇒ 单文件 SQLite，别碰服务化。
- 100 次/天 + 多设备 ⇒ 必须有服务端。

**判据**：说不出这三个数字 = 还没想清楚，别往下走。

### 图 2：数据流（谁产生、谁变换、谁消费）

从左到右一条链，**每段只标「数据长什么样」和「量级」**：

```
[来源]       [变换]        [存储]      [变换]       [消费]
用户输入 →  校验/归一 →    主库   →   查询/检索 →  界面/API
  文本       清洗          百万行      毫秒级       人/agent
```

**三个必须标出来**：
1. 每段的**形状**（一条记录有哪些字段）
2. 每段的**量级**（条数、字节数）
3. 每段的**延迟要求**（毫秒？秒？可异步？）

**最常见错误**：把「用户点一下」和「后台跑一小时」画在同一条链上。必须分开。

### 图 3：状态图（什么东西会变）

| 状态 | 谁改 | 频率 | 改错了怎么办 |
|---|---|---|---|
| 用户数据 | 用户 | 高 | 备份 |
| 计算结果缓存 | 系统 | 高 | 丢掉重算 |
| 配置 | 人 | 低 | 版本控制 |

**最重要的一条判断**：**能重算的都不是真相，别当真相存。**
把「可重算」与「不可重算」混在一张表里，是所有数据设计事故的源头。

### 图 4：模块边界（谁能调谁）

有向图，**箭头只有一个方向**。出现双向箭头 = 边界划错了。

```
API 层 ──→ 业务层 ──→ 存储层
  ↑                        ↑
  └── 前端（只能调 API，不能直连存储）
```

**三条硬规则**：
1. 前端不许直连数据库，哪怕只是读。
2. 业务层不许知道 HTTP；反过来也一样。
3. 存储层不许有业务规则。约束放数据库，判断放业务层。

**判据**：能不能把存储层整个换掉（SQLite ↔ PG），业务层一行不改？
不能 = 耦合了。

### 图 5：信息流（谁需要知道什么，什么时候）

**这与「数据流」不同**：数据流是数据怎么走，信息流是**谁需要被通知**。

| 事件 | 谁要立刻知道 | 谁可以稍后 | 谁不用知道 |
|---|---|---|---|
| 用户写入 | 用户自己（确认） | 其他设备 | 别人 |
| 后台任务完成 | 发起者 | — | 别人 |

**这张图决定要不要 MQ / WebSocket / 轮询。**
大多数个人项目「轮询 + 一个事件表」就够，别上 MQ。

## 4 任务切片（图之后才有）

把工作切成**能独立验证**的块，每块三条：改哪、怎么验、失败长什么样。

```
1. 存储层：加表 X
   改：schema.sql + 一个读写函数
   验：写一条读一条，字段全对
   失败：读回来字段少了 / 顺序变了

2. 业务层：把 X 接进现有流程
   改：handler 里多调一次
   验：接口返回不变，库里多一行
   失败：接口 500 / 多写了两行
```

**切片顺序规则**：
1. **先做「能证明错」的**，不是先做「最容易的」。
2. **每一刀切完都要能跑**，不能出现「三个都改完才能启动」。
3. **存储层永远先于业务层** —— 业务层是基于存储形状写的。

## 5 给用户解释范畴

| 概念 | 一句话 | 它回答的问题 | 弄错了会怎样 |
|---|---|---|---|
| 后端 | 处理数据和规则的地方 | 这个操作对不对、该怎么算 | 前端写了业务规则，换个端就全错 |
| 前端 | 人看到和操作的地方 | 怎么给人看、怎么收人输入 | 前端直接改数据，绕过所有校验 |
| 数据流 | 数据从哪来到哪去 | 一份数据在系统里怎么走 | 同一条数据存三份，三份不一致 |
| 信息流 | 谁需要知道什么 | 什么时候通知谁 | 该通知的没通知，用户以为没成功 |
| 状态 | 什么东西会变 | 现在是什么情况 | 「能重算的东西」被当成真相存下来 |
| 边界 | 谁调谁 | 改一处会不会牵连别处 | 改一个字段，五个地方编译不过 |

---

## 6 常见坑（按出现频率）

1. **先选技术，再想需求**。选完发现不需要，白搭。
2. **把「能重算」和「不能重算」存一起**。后面永远分不清哪个是真的。
3. **只有一个环境**。测试数据和生产数据混在一起，一次误操作全没。
4. **没有「失败长什么样」的定义**。只写成功，出错时无法判断是哪种错。
5. **一次改三层**（存储 + 业务 + 界面）。出问题不知道是谁的。
6. **不做增量**。所有操作「全量重来」，数据一多就崩。
7. **把「实时」当默认要求**。多数场景「最终一致」就够，实时要多付一个数量级。

---

## 7 自检（六条，全过才算规划完）

1. 能一句话说清「谁、什么频率、坏了会怎样」。
2. 能画出数据从输入到输出的完整路径，每段标了量级。
3. 能列出所有有状态的东西，并标出哪些能重算。
4. 能指出前端每一行代码最终调到后端哪个函数（没有悬空调用）。
5. 能把存储层整个换掉而业务层不改。
6. 任务切成 ≥3 块，每块单独能跑、单独能验、单独能回滚。

**六条过不了就别开工。开工之后返工的成本是现在的十倍。**

## 8 与「数据流 / 信息流」主线的衔接

本文件的图 2（数据流）与图 5（信息流）是**规划视角**；
第 R3 段（`r3-two-flows.md`）是**接口视角**（每个字段消费者能推出什么）。

**两者不重复，且都需要**：
- 规划时画不出图 5 ⇒ 你不知道谁该被通知 ⇒ 接口会漏字段
- 接口时答不出「能推出什么」⇒ 图 5 画的是机构不是信息

---

## 9 语气

- 用户是外行不要紧，**先接住再对齐**：「你说的这个其实是两个问题，我们分开看」。
- 不用「这不可行」一棒打死。分三层答：哪层现在能做、哪层要什么条件、哪层最容易翻车。
- 每次只推进一步。不要一次甩五张图。
- 讲概念**先说代价，再给名字**。先给名词会背成空壳。
