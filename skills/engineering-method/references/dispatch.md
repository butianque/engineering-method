# 分发：八类话语怎么判、从哪一层进

> `SKILL.md` 只负责"该不该进门"。**进来之后去哪一步，看这一份。**

---

## 一、八类话语 → 八个入口

| 类 | 用户会说的话（原文锚点） | 本质在问什么 | 入口（层 / 门） |
|---|---|---|---|
| **认知** | 认知不对 / 概念不清 / AI 不懂这个 / 为什么它想不到 / 想不明白 | **我缺什么外部信息** | 认知链 → 回填划界 |
| **范畴** | 定个范畴 / 术语不统一 / 边界在哪 / 这算什么东西 / 属于哪一类 | **这个词到底指什么** | 层一·划界 |
| **立项** | 立项 / 要不要做 / 值不值得 / 从哪开始 / 这个项目做什么 | **它应该长什么样** | 层一·域 |
| **规划** | 规划 / 路线 / 分几步 / 里程碑 / 先做什么后做什么 | **怎么分段交付** | 层一·切片表 |
| **策划** | 策划 / 方案 / 怎么落地 / 怎么给 AI 用 / 有没有别的办法 | **选哪条路、代价多少** | 层一·策划 |
| **设计** | 设计 / 它应该长什么样 / 这个系统怎么做 / 部件怎么接 | **部件之间怎么对接** | 层一·三定 |
| **工程** | 工程 / 架构 / 模块 / 分层 / 耦合 / 依赖 / 重构 / 技术债 / 代码质量 / 可维护 / 跨仓库 / 上游下游 / 部署顺序 / 版本对齐 | **结构怎么放、谁能依赖谁** | **层一·三定 → 层二** |
| **代码** | 写代码 / 实现 / 加个功能 / 加个接口 / 改一下 / 重构一下 / 报错了 / 跑不起来 / 编译不过 / 测试过了 / 能跑了 / 好像没问题 | **动作怎么做、做完算不算完成** | **层一·三定 → 层二 → 门 4** |

### 「工程」「代码」两类为什么单列

**这是最容易被误以为"不用走流程"的两类，也是最常翻车的两类。**

```
「工程」问的是结构（模块 / 分层 / 依赖 / 技术债）
        ⇒ 答案必须落在 设计.md 的三定里，否则是空谈
        ⇒ 只说"要解耦"不写"谁能依赖谁"，等于没说

「代码」问的是动作（加 / 改 / 修）
        ⇒ 动作之前必须有三定（否则又是"零散"）
        ⇒ 动作之后必须有端到端（否则又是一句"测试过了"）
```

**⇒ 这两类**不许直接进"写"**，必须先进层一·三定 的三定。这是 G7 的入口。**

**判据（怎么区分"要不要进门"）：**

| 用户说 | 进不进 | 为什么 |
|---|---|---|
| 「加个接口」 | ✅ 进 | 接口 = 对外承诺 = 有接缝 = 有三定要定 |
| 「这个参数是什么」 | ❌ 不进 | 单点事实，一句话能答 |
| 「改一下这个字」 | ❌ 不进 | 机械修改，无接缝 |
| 「重构一下这个模块」 | ✅ 进 | 结构变更 = 必然有依赖方向要重定 |
| 「报错了，帮我看看」 | ✅ 进（轻量） | 从层一·三定 三定确认，不必重填全套 |
| 「测试过了，可以上线吗」 | ✅ 进 | 这是"声称完成"，触发 G2/G3 |

**为什么必须分入口**：

```
如果"术语不统一"也要填八件套 → 用户立刻觉得这 skill 太重 → 不用了
⇒ 重的东西必须能只取一片
```

## 二、进来第一件事：判层（不是填表）

```
Q1  已经有 立项书？（且域表非空、有边界、有未知项）
      有 → 不重写，往下判
      没有 → 从 层一·域 开始

Q2  已经有 三定？（依赖序 / 依赖方向 / 风格带数字，且设计已签收）
      有 → 跳到 层一·切片表
      没有 → 层一·三定

Q3  已经有 范畴表？（且 3 张表齐）
      没有 → 层一·划界
      有 → 往下判

Q4  已经有 切片表？（且四件东西齐：片 / 两流 / 依赖 / 怎么算过）
      没有 → 层一·切片表
      有 → 层二

Q5  已经有 集成面？（且 7 行齐）
      没有 → 层二·集成面
      有 → 直接跑 gate.sh
```

**⇒ 已有的一律不重写。只补缺的那一块。**

## 三、误伤防护（这是最容易做错的）

### 3.1 "认知"这类最容易被误触发

```
✅ 该触发：「认知不对」「AI 不懂这个」「为什么它想不到」「概念不清」
❌ 不该触发：「这个模型认知能力如何」「认知心理学怎么看」
```

**判别法**：主语是**这个项目 / 这个 AI 的当前理解**才触发；
主语是**泛指的 AI / 学科**不触发。

### 3.2 "设计"这类最容易被当成"写代码"

```
✅ 该触发：「部件怎么接」「契约是什么」「这个系统怎么分」
❌ 不该触发：「这个函数怎么写」「帮我写个 class」
```

**判别法**：问的是**部件之间**才触发；问的是**部件之内**直接做。

### 3.3 单点问题不许进这个门

```
✅ 该触发：「这套东西整体怎么规划」
❌ 不该触发：「这个 API 的参数顺序是什么」
```

**判别法**：答案能一句话说清 ⇒ 不进；需要一份文档 ⇒ 进。

## 四、八个入口各自的"最小可用集合"

**进来只做到够用，不要求全套。**

| 入口 | 最小产出 | 可以暂时不做的 |
|---|---|---|
| 认知 | 一条补给记录（带出处）+ 更新范畴表 | 规划 / 策划 / 设计 |
| 范畴 | 范畴表 3 张表 | 其余全部 |
| 立项 | 域表非空 / 有边界 / 有未知项 | 规划 / 策划 / 设计 |
| 规划 | 立项书 + 规划.md | 策划 / 设计 |
| 策划 | 立项书 + 策划.md | 规划 / 设计 |
| 设计 | 立项书 + 设计.md（含系统设计签收 + **三定**） | 策划可以后补 |
| **工程** | 设计.md 的**三定**（依赖序 / 模块依赖方向 / 风格） | 立项 / 规划可以后补 |
| **代码** | 三定齐 + 集成面 + 验收退出码 0 | 规划 / 策划可以后补 |
| 要声称完成 | 以上全部 + `gate.sh --done` 通过 | — |

**⇒ 越往后要求越严，但前面的关卡不是"必须"，是"越接近交付越必须"。**

**「工程」「代码」两类的特别说明：**

```
工程：可以跳过立项和规划（那是上一个环节的事），但不能跳过三定
      —— 因为"解耦 / 分层 / 重构"如果不落到"谁能依赖谁"，就是一句空话

代码：可以跳过策划，但不能跳过三定 + 集成面 + 验收
      —— 因为这就是"零散"的全部成因
```

## 五、什么时候可以退出这个 skill

| 情形 | 怎么退 |
|---|---|
| 用户说"就按这个做" | 回到正常执行，但**产物文件保留**，随时能跑 gate |
| 用户说"太麻烦" | 降到**最小可用集合**（上面那张表），不放弃 gate |
| 发现判错了入口 | 回本节第二节重判，不要硬走完 |
| 做完了一个阶段 | 停在那一阶段，报告产物，**不要自动往下冲** |

**⇒ 退出不等于作废。文件在，随时能回来跑 gate。**
