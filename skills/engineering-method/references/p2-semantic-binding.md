# P2 — 语义 ↔ 结构绑定

> 本阶段的存在理由：**"把这条需求实现掉"这句话，在没指认落点之前是不可执行的。**
> 自然语言说的是**意图**，代码里存在的是**结构、字段、参数**。中间的这张绑定表，
> 就是把"说不清"变成"指得准"的那一步。

## 0. 它不是什么

| 不是 | 而是 |
|---|---|
| `spec-to-code-compliance`（核对规格与代码**是否一致**） | 把**尚未存在**的需求绑到**已存在**的结构上 |
| spec-kit 式"规格 → 生成新代码" | 绑定**既有代码**：哪个函数、哪个字段、哪个参数 |
| 一份说明书 | 一张**可执行、可回报、可回环**的对照表 |

> 参考：`addyosmani/agent-skills` 曾把类似能力列为提案（issue #103），并自述其粒度"刻意不到
> line-level / private-helper-level"。本阶段要的恰恰是那一级：**参数级**。

## 1. 绑定表 schema（每条需求一行）

| 字段 | 含义 | 硬性要求 |
|---|---|---|
| `req_id` | 需求条目号，**来自 P1 树的叶子** | 必须能对回 P1 |
| `nl_text` | 自然语言原文 | **原样存，不许改写**（改写会丢掉需求方的真实措辞） |
| `semantics` | 语义五元组：**主体 / 动作 / 对象 / 条件 / 量** | 五项都要写；"量"含单位与量级 |
| `binding` | 落点：`file:symbol` · 类型 · 字段 · **参数** · 配置键 · DB 列 · 事件 | 至少 1 个，或显式 `NEW` |
| `binding_kind` | `NEW` / `MODIFY` / `REUSE` / `DELETE` | 必须明确，不许留空 |
| `current_behavior` | **读出来的**现有行为 | 不许写"我猜它…"；读不到就标 `UNKNOWN` 并去读 |
| `expected_behavior` | 期望行为 | 必须可观测（能对应到判据） |
| `dependents` | **改这个落点会牵动谁**：调用点、引用、配置、事件订阅、其它 req | 联动性的载体；漏一个就是不完整 |
| `criterion` | 该点位的判据（测试 / 断言 / 指标） | 必须有；否则这个落点无法验证 |
| `status` | `BOUND` / `UNBOUND` / `CONFLICT` | `UNBOUND` 不许进入实现 |

## 2. 语义五元组怎么拆（防止"想当然"）

| 元素 | 问自己 | 例 |
|---|---|---|
| 主体 | 谁触发？用户 / 系统 / 定时 / 上游服务 | 已登录用户 |
| 动作 | 做什么？（动词要单一） | 修改 |
| 对象 | 作用在什么实体上 | 订单的收货地址 |
| 条件 | 在什么前提 / 排除什么情形 | 未发货；已发货则拒绝 |
| 量 | 数量、阈值、单位、量级 | 一次修改 ≤1 次；窗口 15 min |

> **"量"最容易漏。** 需求方说"要快一点"，量缺失 → 先回去问，或在 P0 里显式标为
> `UNRESOLVED`，**不许自己拍一个数**。

## 3. 绑定的执行顺序（不许跳步）

```
1) 读：先读清楚现有结构（类型定义、字段、参数、配置、调用链），产 current_behavior
2) 判：这条需求是 NEW 还是 MODIFY/REUSE/DELETE
3) 绑：写出 binding（到 file:symbol / 字段 / 参数级）
4) 追：算出 dependents（反向引用、正向调用）
5) 验：每个落点配一条 criterion
6) 回：读的过程中若发现与 P1 假设冲突 → 回 P1 改树（不是改表迁就）
```

**第 1 步不许省。** "先绑了再说"是最常见的失败模式：绑到一个名字像的符号上，
但那个符号根本没有这个行为。

## 4. 联动性与勾连性（本表的真正价值）

`dependents` 不是备注，是**触发器**：

```
规则 D1  改一个 binding ⇒ 必须同步更新其【全部 dependents】
规则 D2  任何 dependents 未确认 ⇒ status 不得为 BOUND（只能是 UNBOUND）
规则 D3  同一 binding 被 ≥2 条需求引用 ⇒ 必须显式标出共享，并在 P3 里合并检验
规则 D4  binding_kind = DELETE ⇒ 必须列出全部引用点，逐个给出迁移或删除的判据
```

数据与参数的"互相嵌套引用"就体现为：**字段 A 的取值依赖参数 B，参数 B 由需求 R2 设定**——
这类链路要在 `dependents` 里显式连起来，否则改 A 会静默破坏 R2。

## 5. 什么时候标 `CONFLICT`

- 两条需求对同一落点提出**互斥的**期望行为；
- 需求与现有不变量（P0 的 Confounds / 代码里的断言）矛盾；
- 语义五元组里"量"与现有约束冲突（如现有字段精度不足）。

`CONFLICT` 不许悄悄"取一个折中"——要么回需求方确认，要么在 P1 里作为承重子节点被 `REFUTED`。

## 6. 与其它阶段的接口

- **进**：P1 树的叶子。
- **出**：`binding` 是 P4 证伪工具的作用对象；`criterion` 是 P3 的判别检验；`dependents` 是回归范围。
- **回**：绑定过程中发现的新事实，必须回 P1 补判；**表不能替代树**。

## 7. 反例（这些写法一律不算绑定）

| 写法 | 为什么不算 |
|---|---|
| `binding: 后端逻辑` | 不是落点，是范围 |
| `current_behavior: 应该是先校验再写库` | "应该"= 没读，等于没绑 |
| 需求写了但 `binding: NEW` 且没写要新建在哪一层 | 等于没设计 |
| 只绑 `file` 不绑 `symbol` / `参数` | 粒度不够，实现时会自由发挥 |
| 落点有了但 `criterion` 空 | 该点是不可验证的，绑定无效 |
| `dependents` 空但该符号全仓有 12 处引用 | 漏算联动 → 回归必炸 |
