# 落位：这类东西放哪（分类与统筹）

> **AI 不缺能力，缺「空间记忆」。**
> 没有空间记忆 ⇒ 只有**就近原则** ⇒ 同类东西散落在十个地方 ⇒ 越积越乱。

---

## 一、现象（真实发生）

```
要测一个功能 → 需要写一个"临时测试接口"
  → 项目里没有 → AI 不知道"这类东西该放哪"
  → 翻代码、翻记录、枚举已有功能
  → 找到一个"看起来能挂进去"的地方 → 塞进去
  → 测完，接口留着（没人知道它是临时的）
  → 下次再测，又要重来一遍
```

**拆成四个独立缺失：**

| # | 缺失 | 表现 |
|---|---|---|
| **P1** | **归类** | 临时测试接口算"测试设施"还是"调试工具"？ |
| **P2** | **落位** | 没有 `test-support/temp/` 这种约定位置 |
| **P3** | **清单** | 得枚举现有功能才知道能不能复用 |
| **P4** | **生命周期** | 用完不清理，越积越多 |

**⇒ 四个都不在"代码对不对"这个维度上。测试、类型检查、lint 一条都管不到。**

---

## 二、为什么人不会，AI 会

| | 人 | AI |
|---|---|---|
| 记忆载体 | 长期记忆 + 肌肉记忆 | **当次上下文**（用完就没） |
| 空间感 | 有（"我知道那个文件在哪"） | **无**（只有路径字符串） |
| 习惯 | 累积形成 | **不累积**（每次从零） |

**⇒ AI 只有"就近原则"：放在最近改过的那个文件旁边。**
**⇒ 结果：同类东西散落。**

**⇒ 这不是能力问题，是载体问题。改提示词不改载体。**

---

## 三、解法：用「落位表」代替记忆

**核心判断：**

> **不是让 AI 变聪明，是让它有一个**查得到的位置**，而不是每次都要**推断**位置。**
> **查表是 AI 强项，推断是 AI 弱项。**

### 3.1 落位表长什么样（放进 `设计.md`）

```markdown
| 这类东西 | 放在哪（目录/包） | 命名规范 | 生命周期 |
|---|---|---|---|
| 临时测试接口 | test-support/temp/ | temp_<用途>_<yyyymmdd> | 30 天后删 |
| 一次性脚本 | scripts/oneoff/ | <yyyymmdd>-<用途> | 用完即删 |
| 长期测试设施 | test-support/ | 不许带 temp | 长期 |
| 调试开关 | debug/flags.go | 统一注册 | 长期 |
```

**四条规则：**

```
R1  每一类必须有唯一位置（不许"看情况"）
R2  临时类必须有 TTL（不许"以后再说"）
R3  新东西先查表再动手
R4  查不到 = 表不全 = 先补表，不许裸放
```

**R4 是关键**：它把"AI 推断位置"变成"AI 补表"，而**补表是可检查的**。

### 3.2 覆盖哪四类（先够用，不求全）

| 类 | 典型东西 | 默认位置建议 |
|---|---|---|
| **入口** | 路由 / CLI 命令 / 事件处理器 | `api/` 或 `cmd/` |
| **设施** | 测试工具、fake、fixture、helper | `test-support/` |
| **临时** | 一次性脚本、调试接口、探针 | `scripts/oneoff/` · `debug/temp/` |
| **配置** | 开关、阈值、feature flag | `config/` 或 `debug/flags.go` |

## 四、能自动化的部分（S1–S4）

| # | 能力 | 判据 |
|---|---|---|
| **S1** | 要求"落位表必须先有" | `设计.md` 含落位表且非空 |
| **S2** | 要求"每类有唯一位置" | 每行"放哪"列非空 |
| **S3** | 要求"临时物有 TTL" | 生命周期列非空 |
| **S4** | 检查"新文件是否落在已声明位置" | 文件路径匹配不到任何行 ⇒ BLOCK |

**⇒ 这四条都是一条命令能判的。**

---

## 五、做不到的部分（必须归 pangu 工作台）

**这一段要原样告诉用户，不许含糊。**

| # | 做不到 | 为什么 |
|---|---|---|
| **N1** | 自动发现"这里需要一个新类" | 语义判断（临时 vs 长期） |
| **N2** | 自动决定"这个新类该叫什么" | 命名是语义决策 |
| **N3** | **跨会话记住"上次那个在哪"** | **skill 无状态** |
| **N4** | 主动清理过期临时物 | 需要后台进程 + 时间感知 |
| **N5** | 在写代码的瞬间提醒"放错了" | 需要宿主钩子（`pre_tool`） |
| **N6** | 从多次操作归纳"这个项目的习惯" | 需要跨会话学习 |

**⚠️ N3 是根本限制：**

```
skill = 一段文本 + 无状态 ⇒ 不能记住
⇒ "上次那个临时接口在哪" skill 永远答不了
⇒ 只能靠人记住，或者写进文件
⇒ 写进文件就叫"落位表"
```

**⇒ 所以 S1–S4 是 N3 的降级方案：不靠记忆，靠登记。**

## 六、诚实边界（完整表述）

```
本 skill 能做的：
  ✅ 要求你有一张落位表
  ✅ 检查新文件是否落在已声明位置
  ✅ 检查临时物有没有 TTL
  ✅ 检查模块依赖方向有没有越界

本 skill 做不到的（必须等 pangu 工作台）：
  ❌ 自动发现"这里需要一个新类"        —— 语义判断
  ❌ 自动决定"这个新类该叫什么"        —— 语义判断
  ❌ 跨会话记住"上次那个在哪"          —— skill 无状态
  ❌ 主动清理过期临时物                —— 需要后台进程
  ❌ 在写代码的瞬间提醒你放错了        —— 需要宿主钩子
  ❌ 从多次操作归纳"这个项目的习惯"    —— 需要跨会话学习

替代方案（为什么现在能凑合）：
  没记忆 → 用文件代替记忆（落位表）
  没钩子 → 事后跑脚本（arch-check.sh）
  没后台 → 手工定期跑
  没语义判断 → 人在设计阶段填表
```

**⇒ 详尽的论证与 pangu 需求清单在**
`系统工程立项开发器/00-市场认知/19-分类与统筹.md`

## 七、和市面工具的关系

| 工具 | 管什么 | 管不到什么 |
|---|---|---|
| ArchUnit / archfit | **依赖方向、环、层越界** | 归类（P1）、清单（P3）、生命周期（P4） |
| dependency-cruiser | 同上（TS） | 同上 |
| Nx boundaries | 模块边界 | 同上 |
| **没有工具** | — | **P1 / P3 / P4** |

**⇒ 市面上只解决"越界"，不解决"归类"和"生命周期"。**
**而"临时测试接口"这个例子，恰好是后两个。**
