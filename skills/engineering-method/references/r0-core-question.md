# R0 立核：把一个请求还原成一个核心问题

## 1 为什么要这一步

用户的请求几乎**从来不是核心问题**。它是一句**症状描述**，或者一个**他想让你做的事**。

- 「接口太僵硬」→ 核心问题可能是「模型被拆成两半，谁也接不上谁」
- 「这里的数字不对」→ 核心问题可能是「判据的值域错了，不是数值错了」
- 「我觉得可能还是认知问题」→ 核心问题可能是「术语覆盖率只有 46%，一半概念没有唯一权威」

**照着请求做，你会解决症状。找出核心问题，你会消掉一类症状。**

---

## 2 操作：三问降维

对用户的原话，连续问三次：

### 问 1：他在描述**现象**，还是**机制**？

| 如果是现象 | 继续问 |
|---|---|
| 「这个接口这样写很僵硬」 | 僵硬在哪？为什么这样写？写的人当时缺什么？ |
| 「这两个数不一样」 | 哪个数对？为什么会有两个？它们数的**是同一个东西**吗？ |
| 「我没办法判断」 | 他缺的是**信息**，还是**词汇**，还是**判断权**？ |

### 问 2：这件事如果只做表面，**下次还会不会发生**？

会 → 你找的是现象，不是机制。
不会 → 可能已经到机制层了，但仍要问第三条。

### 问 3：**什么才算解释清楚了**？

这一条必须写下来，它是后面所有递归的验收标准。

例子（真实）：
> 「AI 想要了解苹果，回忆出来的内容能够解释苹果这个词的所有词都包含在内。」

这句话就是**验收标准**，它能被判真假：
```
忆「苹果」→ 返回里必须出现「红」「青」「甜」这类能解释苹果的东西
```

对照：如果当初写成「优化接口返回」，那什么都能算完成。

---

## 3 核心问题的正确写法

**格式**：
```
【核心问题】<一句话，问的是机制不是现象>
【解释标准】<什么样的输出能证明它被回答了；可判真假>
【不解释什么】<明确排除的范围，防止无限扩张>
```

**判据**：
- 核心问题里**不许出现**具体文件名、行号、数字（那是证据，不是问题）；
- 解释标准必须能写成一条**可执行检查**（命令 / 断言 / 一份具体的预期输出）；
- 「不解释什么」必须有至少一条。**没有边界的核心问题会吞掉整个项目。**

---

## 4 常见错误

| 错误 | 表现 | 后果 |
|---|---|---|
| 把请求当问题 | 用户说要 A，就只做 A | 症状消了，病还在 |
| 问题太大 | 「如何做对系统」 | 无法判真假 |
| 问题太小 | 「修这个 bug」 | 治不了同类 |
| 没有验收标准 | 「改好一点」 | 永远不知道何时停 |
| 把方案当问题 | 「需要加一个接口」 | 锁死了错误的解法 |

---

## 5 实战例子

**用户**：「1 维读一个 2 维读一个，到底在读什么？这些数据不是同一个超图吗？我不认为这正确。」

**错误的 R0**：「修 `Dim` 和 `Composition.Dim` 的数值不一致。」（现象 + 方案）

**正确的 R0**：
```
【核心问题】「维」这个量，我们到底在算什么？它是不是本来就该由工具算？
【解释标准】同一个节点、同一份数据，任何接口给出的「维」必须一致；
            且这个量必须能对应用户说的「苹果一条内有红、青、甜」。
【不解释什么】不解释「四维及以上」（用户明确说先不管）。
```

**结果**：挖到了用户一年前的原话「维就是维……长度不是维度」
「工具不计算维」——**整个方向被推翻**，不是修数值，是**这个函数不该存在**。

---

## 6 与后续阶段的接口

R0 的输出直接喂给 R1：
- 核心问题 → 拆成 N 个递归问题
- 解释标准 → 每个递归问题的判据
- 不解释什么 → 递归的**停止边界**（防止一直挖下去）
