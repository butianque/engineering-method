# R2.5 外部检索：不知道就搜，别猜

## 1 为什么这是一条独立的规则

**因为「不知道」有两个来源，而对它们的反应完全不同：**

| 不知道的来源 | 常见反应 | 正确反应 |
|---|---|---|
| 内部：这个仓库怎么做的 | 去读代码 | ✅ 对 |
| **内部：这个设计对不对** | **凭经验判断** | ❌ **去搜业界怎么做的** |
| 外部：别人怎么解决这个问题 | 凭印象 | ❌ **去搜，别凭印象** |
| 外部：有没有成熟产品 | 直接自己发明 | ❌ **先看，再决定造不造** |

**最大的漏洞是第二行**：
内部约定常常是「重新发明了一个别人早解决过的问题」，
而你**只翻了仓库，没翻世界**，于是把「本仓库的奇怪做法」当成「唯一做法」。

---

## 2 触发条件（命中任一就搜）

```
□ 你正在说「应该是这样吧」「大概是这样」「我记得好像」
□ 有两个解释都说得通，你在凭感觉选
□ 你要发明一个机制（命名、流程、格式、判据）
□ 你在给一个「内部约定」做辩护
□ 你发现某个设计「很奇怪，为什么当初这么做」
□ 用户说「你看看别人怎么写的」「参考成熟产品」
□ 你要写一条判据，但不确定这样判对不对
□ 同一个问题你修了第二次
```

**判据**：**当你在猜，停止猜。**

---

## 3 搜索的优先级（成本从低到高）

```
① 本地已有源码      → 最快，可 grep，可读实现
② 官方规范/文档     → 权威，有义务写清边界
③ 网络搜索          → 补「不知道存在」的东西
④ 论文 / 标准       → 只有前三个都答不了时才去
```

**先 ① 后 ③，但别停在 ①。**

真实教训：某项目要设计「给 AI 的记忆接口」，
一开始只读自己仓库 → 得出「业界没有无分数检索」的结论（错）。
去搜之后发现 **Lucene `ConstantScoreQuery` 明确「剥掉所有分数」**、
**S3 `ListObjectsV2` 用字典序 + 不透明游标在无排序下分页**。
**结论从「我们是唯一」变成「我们有先例，但要补两件事」。**

---

## 4 搜什么（四类，缺一不可）

### ① 成熟产品怎么做的

不是「有什么功能」，是**「它的接口长什么样」**。

要拿到：返回结构的字段清单、错误怎么表达、分页怎么分、边界怎么划。

### ② 官方规范的原文

不是二手博客的转述。要能引到规范里的一句话。

### ③ 反例：谁试过，失败了，为什么

**这一类价值最高，也最常被跳过。**
看失败案例比看成功案例更能避开坑。

### ④ 「没有先例」也要记录

如果搜完确实没有，**写下来**，并写清搜了哪些关键词、在哪些地方搜。
「无先例」是一个能改变设计决策的事实，不是「没搜到」。

---

## 5 搜完怎么用（三个反模式）

| 反模式 | 表现 | 正确做法 |
|---|---|---|
| **抄代码** | 把别人的实现贴过来 | 只抄**机制**，自己写实现 |
| **抄外观** | 抄目录结构、命名、UI | 只抠「它把哪个不确定性换成了哪个事实」 |
| **当成绝对权威** | 「某某项目这么做，所以我们也要」 | 记录**它当时的前提**，检验你的前提是否相同 |

**判据**：
> 从别人那里拿来的每一条，必须能回答「**它解决的具体问题是什么**」。
> 答不出 = 你在抄，不是在学。

---

## 6 检索结果的记录格式

```markdown
### <来源名> — <一句话它解决了什么>

**定位**：URL / 仓库路径 + 文件:行
**证据等级**：官方规范 / 有实现可读 / 只有注释 / 二手转述
**它的做法**：<具体，带字段/参数>
**它的前提**：<它假设了什么；你不一定具备>
**对本案的用处**：采纳 / 部分采纳 / 仅参考 / 不适用（说明为什么）
```

**「证据等级」一栏不能省。**
把「注释里写的」当成「有实现」，是整个项目最容易犯的错。

真实案例：某还原仓库里 `contextCollapse/index.ts` 的实现体被抹掉，
只剩 `export function isContextCollapseEnabled(): boolean { return false }`。
如果不去看函数体，就会把「桩」当成「真身」，得出完全相反的结论。

## 7 搜索的方法（具体操作）

### 7.1 关键词怎么起

```
第一轮（宽）：  <领域> + <要解决的问题>
              例：「memory interface LLM context」
第二轮（窄）：  <已知的最接近的实现> + <具体机制>
              例：「S3 ListObjectsV2 cursor pagination」
第三轮（术语）：搜「有没有专门的词描述这件事」
              例：搜到 ConstantScoreQuery 才发现「无分数检索」有正式名字
```

**第三轮最重要**：有了术语，你才能搜到第二、三手资料。

### 7.2 什么时候停下来

- 找到 ≥2 个独立来源说同一件事 → 可以停
- 找到 1 个官方规范 → 可以停
- 所有来源互相矛盾 → 继续，直到找到**差异的根源**
- 三轮无结果 → 记录「无先例」并继续（不要无限搜）

### 7.3 并行检索

多个独立方向**同时派出去**，不要串行等。
每个方向给的任务书要包含：
- 背景（一句话这个系统是什么）
- **要回答的具体问题**（3–5 个，不能是「调研一下」）
- 输出格式
- 纪律（每条结论带出处，找不到就写「未找到」，不许编）

## 8 与主干的关系

```
R2 递归（挖到机制）
  ↓ 卡住 / 在猜 / 要发明
R2.5 外部检索  ←── 本文件
  ↓ 拿到了先例或反例
回到 R2 修正机制判断
  ↓
R3 双流
```

**检索不是「补充材料」，它会改结论。**
如果搜完你的结论一个字都没变，要么你搜得太浅，要么你本来就知道。

- [ ] 内部问题（这个设计对不对）我搜了吗，还是只翻了代码？
- [ ] 至少看了：成熟产品 / 官方规范 / 反例 三类？
- [ ] 每条结论标了证据等级（规范 / 实现 / 注释 / 转述）？
- [ ] 我抄的是机制，不是外观？
- [ ] 「无先例」的情况我记录下来了吗？

## 10 搜法升级：普通搜法无效，必须"借别人的轴"（2026-11-13 补）

### 为什么会话里搜了也没用

```
你搜什么，取决于你想到什么框架
⇒ 搜索会继承你的框架
⇒ 光搜「X 最佳实践」，得到的只是你已知框架内的更多细节
```

**⇒ 换不到新轴，等于没搜。**

### 四种能"借到别人的轴"的搜法

| 搜法 | 借到什么 | 为什么有效 |
|---|---|---|
| **`X vs Y`** | 别人在用**两个轴**对比 | 直接暴露"还有另一个维度" |
| **`why X fails` / `X anti-pattern`** | 别人的**失败分类** | 失败分类本身就是一种轴 |
| **`X taxonomy` / `X 的几种架构`** | 别人的**分类表** | 分类表 = 轴清单 |
| **`后人批评 X` / `X criticism`** | 别人的**反例** | 反例 = 换画布 |

### 实例（本项目真实发生）

```
搜「agent architecture beyond agent loop」
  ⇒ 拿回「引擎编排 vs prompted orchestration」
  ⇒ 那是我原来没有的轴（我原来只有"用不用 loop"一个维度）
```

**如果只搜「agent loop 怎么优化」，得到的全是 loop 内的调参技巧。**

### 判据：搜完能不能说出"一条原来不知道的事"

```
说不出 ⇒ 白补，换搜法（往上面那四种靠）
说得出 ⇒ 记进检索记录（第 6 节格式），带出处
```

### 四种补给来源（按成本从低到高）

| # | 方式 | 算成功 | 对应本文哪节 |
|---|---|---|---|
| 1 | 读自己的仓 | 找到 ≥1 处可抄的实现 | §3 优先级 1 |
| 2 | 借鉴相似成品 | 找到 ≥1 个可用结构决策 | §4 ① |
| 3 | 搜论文 / 社区 | 找到 ≥1 条带出处的结论 | §4 ②③ |
| 4 | **引入别的学科**（数学/物理/生物/化学） | 找到可迁移的结构 | 本节 §10 之后 |

**第 4 种的特殊之处**：它借的是**结构**，不是结论。

```
例：从"突触会疲劳"借到"同一框架用久了必须强制打断"
例：从"睡眠交替"借到"改一处必须立刻全量回归，不能攒到最后"
```

**这类借用必须标注为 `assumption`（因为可迁移性未经检验），不许当 `cited`。**
