# R3 分流：数据流 ≠ 信息流

## 1 定义

| | 数据流 | 信息流 |
|---|---|---|
| 承载 | ID、坐标、指针、字节 | 读法、前后文、为什么 |
| 消费者 | 机器 | **AI / 人** |
| 判据 | 能算 | **能推出东西** |
| 缺失症状 | 算不出来 | **「能用但读不懂」** |

**接口只交数据流，就是没交信息流。功能「能跑」不等于「被实现了」。**

---

## 2 最典型的失败：语义化的零值

```json
{"target": 0}   // 字段注释：「0 = 这个落点不在库里」
```

程序看：`0` 是个有效哨兵值，逻辑正确。
**消费者看：一个 0，什么也推不出来。**

而同一份数据里**明明有答案**：
```json
{"target": 0, "text": "是红"}   // 一行代码就能给
```

**判据（每个对外字段都问一遍）**：
> **消费者看到这个值，能推出什么？**
> 推不出任何东西 → 这条信息没交出去。

---

## 3 三种补法

### 补法 1：给字，不给号

任何「指向一个节点」的字段，旁边必须有它**读作什么**。

### 补法 2：拆成「前 / 落点 / 后」

只给整句 `苹果是红的`，消费者还得自己找「苹果」在哪、后面是什么。
拆成：
```
[ 前 | 落点 | 后 ]
[    | 苹果 | 是红的 ]
```
消费者直接读到「苹果后面是是红的」。

**这一个拆分，往往就是从「数据」到「解释」的全部差别。**

### 补法 3：截断必须自报

`truncated: true` 说不清少了多少。
必须给 `count + total`。

原因：**任何「全给」的承诺都有失效那天**，失效时消费者必须知道**缺了多少**，
否则它会以为自己看到了全部。

---

## 4 双流清单（每个功能都要填）

```
功能名：<一句话它是什么>
─────────────────────────────────────
数据流
  输入：<谁产生、什么格式、什么坐标系>
  输出：<ID / 坐标 / 字节>
  消费者：<程序 / 测试 / 下游服务>
  失败时：<怎么判断它坏了>

信息流
  输出：<读法 / 前后文 / 人话>
  消费者：<AI / 人>
  它能推出什么：<具体写出来>
  缺失时症状：<消费者会看到什么假象>

记录
  这条信息怎么被**下一次**正确理解：<文档位置 / 字段注释 / 判据>
```

**「它能推出什么」这一栏必须写具体**。
写「能理解这个节点」= 没写。写「能知道苹果后面是红的」= 写了。

---

## 5 一个反向判据：**删掉测试**

> 把这条信息流字段删掉，会有任何**可执行的检查**变红吗？

不会 → 这条信息流**没有判据**，它随时会被下一次重构删掉。
必须补一条测试把它钉住。

---

## 6 常见误区

| 误区 | 纠正 |
|---|---|
| 「结构完整就是功能完整」 | 结构在 L3，功能在 L5 |
| 「JSON 里字段都有就行」 | 有字段 ≠ 有信息 |
| 「AI 自己会查」 | 接口让消费者自己回查，等于没交 |
| 「加了注释就算说清」 | 注释是给读代码的人，不是给消费者的 |
| 「全部返回就对了」 | 要报 `total`，否则消费者不知道缺没缺 |

---

## 7 与 R4 的关系

双流清单直接变成文档的骨架：
- 数据流那半 → 接口规格 / 结构定义
- 信息流那半 → 消费者说明 / 用途

**只写数据流那一半的文档，就是「说明书里只有电路图，没有它能干什么」。**
