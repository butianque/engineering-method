# R4 落盘：文档怎么写才算「下次还能用」

## 1 核心要求

**任何工程或小功能，哪怕是一个端点、一个字段，都要记录：它到底是干什么的。**

不是记录「怎么写的」，是记录 **它是什么、为谁、怎么被读懂、坏了怎么定位**。

---

## 2 目录结构（按认知层分，不按技术分）

```
0.0.X/
├── README.md              索引：这份文档集回答什么问题
├── 01-立项/               为什么要做（核心问题 + 解释标准）
│   ├── 01-立项书.md
│   └── 02-范畴体系.md      ← 关键：定义"有哪些层、每层管什么"
├── 02-架构/               整体怎么转（数据流总图）
├── 03-数据/               存了什么（结构 + 不变量）
├── 04-接口/               对外契约（数据流 + 信息流两条）
├── 05-借鉴/               别人怎么做的（含 URL / 文件:行）
├── 06-工程细则/           编码 / 测试 / 变更流程
├── 90-决策记录/           ADR：每个决定 + 为什么 + 何时可推翻
├── 91-审计/               发现的问题 + 为什么之前没发现
└── 92-概念审计/           逐概念的数学↔规范↔代码 差距
```

**为什么按层不按技术**：技术分类（前端/后端/数据库）会**切断**同一概念的上下游，
而认知层的分类让「同一件事在不同层的样子」并排可见。

---

## 3 每篇文档的固定头部

```markdown
> **状态**：草案 / 现行 / 已作废　｜　**日期**：YYYY-MM-DD
> **取代**：<被本篇取代的旧文档>　｜　**被谁取代**：—/<新文档>
> **基线**：<commit / 版本>
```

**「已作废」的文档必须保留，并写清「为什么作废」+「取代者是谁」。**

理由：作废的稿子里往往有**用户的原话**，那是唯一能推翻后来共识的东西。
**删了它就永远找不回来了。**

---

## 4 每个功能片段的记录模板

```markdown
### <功能名> — <一句话它是什么>

**位置**：`文件:行`（用符号名，不用裸行号；必须用行号时绑 `#token`）

**它干什么**：<一句人话，说清"解决什么问题"，不是"做了什么操作">

**数据流**
- 输入：<谁给、什么格式>
- 输出：<ID / 坐标 / 字节>
- 消费者：<程序 / 下游 / 测试>

**信息流**
- 输出：<读法 / 人话 / 前后文>
- 消费者：<AI / 人>
- **它能推出什么**：<必须写具体结论>

**AI 能看到什么**：<逐字段写>
**用户能看到什么**：<界面 / 响应>

**语义**：<这个词在术语表里的编号 + 定义>

**坏了怎么定位**
- 症状：<观测到什么说明它坏了>
- 判据：<一条能跑的命令>
- 常见误判：<曾经以为是 X，实际是 Y>
```

**「常见误判」这一栏不能省。** 它是下一个人的捷径。

---

## 5 判据文档的写法

**每条判据必须有四件套**：

```
【数值/结论】 具体数或断言
【语料】     什么输入产生的
【口径】     怎么量的（命令 + 参数）
【日期】     什么时候
```

缺任何一件，这个数字**不可复算**，等于没写。

**禁止**：
- 只写「性能提升了」（没数）
- 只写「3700 倍」（没算式）
- 写「约 61ms」（口径丢失）
- 引用「见某文档」（互文，不是事实锚）

---

## 6 指针规则（血泪教训）

**行号是坐标，会腐烂。符号不会。**

```markdown
❌ `core/entity.go:244`          ← 函数移到 :413 之后，这条指向注释
✅ `core/entity.go#computeReadingLocked`
⚠️ `core/entity.go:413`          ← 允许，但必须同时写函数名
```

**实测教训**：某项目 `spec/10` §4 的 12 条指针里 **9 条指错**（最大偏移 +135 行），
另一份预注册件的 21 条锚点里 **15 条失效**。
原因都是「文件加了上百行，文档没跟上」。

**推论**：任何「行号必须精确」的检查，都会随代码演进而集体失效。
**必须换成内容锚**（该行/该函数附近含某符号）。

---

## 7 决策记录（ADR）的写法

每个**改变方向**的决定，写一条：

```markdown
## ADR-NNN <标题>

**日期**：<YYYY-MM-DD>　**状态**：采纳 / 已推翻

**背景**：<当时面对什么，为什么非决定不可>

**选项**：
- A：<做法>　代价：<X>
- B：<做法>　代价：<Y>

**决定**：<选了哪个>

**理由**：<为什么，引用证据或用户原话>

**何时该推翻**：<写一个可观测的触发条件>
```

**「何时该推翻」是最重要的一栏。** 没有它，ADR 会变成教条。

---

## 8 冻结契约的处理

有些形状被用户明确冻结（「这个响应必须 5 个键」）。

**规则**：**不许为了让新字段通过而改断言。**

正确做法：
1. 新能力做成**显式开关**（`?explain=1`），默认形状逐字节不变；
2. 在文档里写清「为什么默认关」；
3. 若确实要改冻结契约，走 ADR，写清代价。

**反例（必须避免）**：改了字段 → 测试红了 → 改测试断言 → 全绿。
**这等于把判据改成了自己想要的结果。**

---

## 9 文档自检

- [ ] 每篇都有状态/日期/取代者
- [ ] 每个功能片段都写了「它干什么」和「它能推出什么」
- [ ] 每个数字都是四件套
- [ ] 指针用符号，不用裸行号
- [ ] 每条 ADR 都有「何时该推翻」
- [ ] 自己犯的错也记了
- [ ] 作废的文档保留着，且写明作废原因
- [ ] 文件名能看出「它回答什么问题」
