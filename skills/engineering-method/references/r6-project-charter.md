# R6 立项：域是推出来的，不是列出来的

> **这一份解决的是**：立项写完，项目还是越做越散；用户的要求永远说不全；图纸每次都要打补丁。
>
> **一句话**：**域 = 范畴 = 「要让这件事成立，必须存在的一类东西」。数量由问题推出，不由模板给出。**

---

## 0 先把「域」这个词钉死

```
域 ≠ 目录  ≠ 章节  ≠ 模板里的第 N 项
域 = 范畴 = 一类问题 + 它的词汇 + 它的边界 + 它的判据
```

**判据（一个域成立的唯一标准）**：

```
删掉这个域，系统会以什么方式坏？
   说得出坏法 ⇒ 它是域
   说不出    ⇒ 它是细节，归到别的域里去
```

**为什么必须这样判**：域的作用不是「把文档分类」，是**让一类问题有词汇**。
一层没有词汇 ⇒ 那层不可能有检查条目 ⇒ 那层的问题永远看不见（`r1-cognitive-layers.md` §5）。

**⇒ 所以「本项目有几个域」这个问题没有通用答案。它只能推。**

---

## 1 五步推导（缺一步，图纸必然要打补丁）

```
① 推   功能 → 困境 → 要成立必须有什么        得到候选域
② 划界 每个域：管什么 / 不管什么 / 怎么算过    得到边界与判据
③ 引导 把要求从用户嘴里提出来（他通常只说一半） 得到能判的条文
④ 兜底 用户不知道 ⇒ 问行业到底怎么做          得到 assumption + 依据
⑤ 落实 不打补丁地写进文档                    得到基线
```

**顺序不许换**：先推域，才知道该问什么；先问清，才知道该查什么；查完才落文档。

---

## 2 推：从「功能」推到「域」

### 2.1 起点不是功能名，是它要消掉的困境

```
用户说：我要一个 X 功能
问自己：X 成立之后，什么困境消失了？
```

| 用户说的 | 不是「做什么」 | 是「什么困境消失」 |
|---|---|---|
| 加个登录 | 写登录接口 | 换设备后仍被认作同一人 |
| 加个缓存 | 接 Redis | 同一查询 N 秒内不重复打上游 |
| 做个记忆库 | 存文本 | 回忆时能交出「能解释这个词的东西」，而不是一条 id |

**⇒ 这一步答错，后面所有域都推错。**

### 2.2 推域的问法（一条一条问，不许一次推完）

```
要让上面那个困境消失，必须同时存在哪几类东西？
   A 类：没有它，X 根本跑不起来
   B 类：有了它，X 才能被别人用
   C 类：有了它，X 才能被证明是对的
   D 类：有了它，X 才能在真实条件下不崩
```

**每答出一条，「域」加一；答不出来就问「删掉它会怎么坏」。**

### 2.3 三类必须被追问出来的域（最常漏）

| 类 | 问法 | 漏了会怎样 |
|---|---|---|
| **词与边界** | 这几个词各自指什么？什么不算它？ | 一义多名、名实不符；后面每份文档各说一套 |
| **消费者** | 谁在什么时机用它？失败时谁受影响？ | 能力都做完了，从没接出去 |
| **判据** | 怎么算过？红哪一条不许合？ | 「测试绿了」被当成完成 |

**注意：这三类不是「必须有的三个域」，是三个必须被问过的问题。** 问题可能有答案、可能落进别的域、也可能被写成「本版不做」。

### 2.4 收敛条件（推够了没有）

每个候选域都要能回答这四句，答不齐就还没推完：

```
1 它管什么（名词在这一域里的意思）
2 它不管什么（边界）
3 它的产物是什么（表 / 图 / 定理 / 判据 / 接口）
4 删掉它，系统以什么方式坏
```

### 2.5 域与域的关系：串 / 并 / 汇

```
串：A 的输出是 B 的输入（B 不许反过来依赖 A）
并：A 与 B 互不依赖，可同时做
汇：X 依赖上面全部（通常是「消费者」与「判据」）
```

**规则：串链每一环只依赖它前面那环。反向依赖 = 环形 = 谁也改不了。**

---

## 3 划界：每个域交三件套

| # | 交什么 | 判据 |
|---:|---|---|
| 1 | **管什么** | 这个域里的每个词，都有一句定义 + 一个反例（看起来像但不是） |
| 2 | **不管什么** | 至少一条；写不出 ⇒ 这个域会吞掉整个项目 |
| 3 | **怎么算过** | 一条命令 / 一次操作 / 一个可数的量；验不出 ⇒ 等于没有 |

**外加一条**：**这个域有词汇吗？** 没有词的那一层，先造词，再提问。

**边界的物理形态**：域表 + 「不做清单」。没有不做清单，任何东西都能被说成「做完了」。

---

## 4 引导：把要求从用户嘴里提出来

**用户的表述永远是一半的。** 不是他不配合，是**他脑子里那部分还没被问成句子**。

### 4.1 六种问法（按有效度排）

| # | 问法 | 为什么有效 |
|---:|---|---|
| 1 | **给两个具体选项，各带代价**：「A 快但库会胀；B 省空间但第一次读要算。选哪个？」 | 判断比构造省力 |
| 2 | **给行业默认值，让他否决**：「一般这么做，你要改就说」 | 否决只要一个字 |
| 3 | **反推边界**：「如果这个不做，会发生什么？」 | 从「不做的后果」定范围 |
| 4 | **对齐他的原话**：「你刚说的是 X，我理解成 Y，对吗？」 | 他已有的话是权威，你只做对齐 |
| 5 | **要他给一个可判的判据**：「什么情况你能一眼看出它没做到？」 | 把感觉变成判据 |
| 6 | **一次只问一个，问完立刻落条文** | 一次问三个 = 一个都不会答 |

### 4.2 三条禁止

```
❌ 「你想要什么样的？」          → 开放题，用户会给你一句愿景
❌ 一次问五个问题                 → 他只答最后一个
❌ 问完不落文档                   → 下一轮答案就飘了，再问一遍
```

### 4.3 判据

```
每个问题都必须能被答成一句可判的话。
答不成 ⇒ 是问法错了，不是用户不清。
```

**⇒ 这条是本 skill 里唯一「怪自己」的判据。** 用户说不清的地方，先改问法。

---

## 5 兜底：用户不明确时，权威临时转移到「行业怎么做」

**这是「不打补丁」的前提。** 一个域如果只靠猜填上，后面必然要改，改就要打补丁。

### 5.1 什么时候转

```
用户明确说了        → 他的话是权威（原话账本）
用户说「不知道」/ 说得很含糊 → 停止追问，转行业
行业也没有         → 记为未知项（不是编一个）
```

### 5.2 行业怎么算「清楚知道」

**不许写「一般来说」。** 判据：说得出下面三样：

```
1 谁这么做（同类系统 / 标准 / 成熟实现，具体到名字）
2 它为什么这么做（解决了什么约束）
3 代价是什么（性能 / 复杂度 / 运维 / 迁移）
```

### 5.3 三条纪律

```
① 行业做法进来时，必须标 assumption，不许冒充用户要求
② 给出后仍要回到用户：「这条我按行业默认写了，要改就说」—— 否决权在他
③ 行业也空白 ⇒ 写进未知项：不知道什么 / 打算怎么验 / 什么时候必须解决
```

**⇒ 未知项不是缺陷，含糊才是。写「不知道 X，打算用 Y 验」是合法状态；留空是最坏的一种谎。**

---

## 6 落实：不打补丁地写进文档

**「打补丁」不是排版问题，是同一份文件里并存两套说法，读者无法判断哪句生效。**

### 6.1 六条硬规

| # | 规 | 禁止 | 要求 |
|---:|---|---|---|
| **D1** | 只写当前真相 | 修订记录、补记、「原写…现改为…」、变更日志段 | 旧句子**直接替换**成新句子；历史留在 git |
| **D2** | 插入 / 替换 / 删除，三选一 | 追加到末尾当「补充说明」 | 插到它应在的位置，不改别的节号 |
| **D3** | 一个概念只有一处 | 同一概念两份文档各定义一次 | 其余处只引用，不复述 |
| **D4** | 文件数只减不增 | 为「补充」新建文档 | 新增须有它**独占的概念** |
| **D5** | 编号不复用、不递增 | 删除后让后来者补位 | 前缀一经分配永不给别的域；删除留空 |
| **D6** | 完成改状态，不重读 | 让下一个 agent 从读一遍已完成文档 | 只改状态表一行 + 证据指针 |

### 6.2 改一处，顺着串链改下游

```
串链：词与边界 → 系统结构 → 工程结构 → 模块 → 写法
改上游不改下游 ⇒ 下游全错，而测试测不出来（不存在的东西不产生红色）
```

**⇒ 每份文档开头写一行「我依赖谁」，改上游时按它反查下游。**

### 6.3 状态的物理位置

```
状态表：文档 / 草案·定稿·作废 / 证据指针
规则：接手先读状态表；「定稿」只读一行，不读正文；没有证据指针的「定稿」按草案算
```

**为什么单列**：用户的原话是「已经完成的任务，却又要重新读一遍这种问题，浪费时间还浪费资源」。
修法不是让 AI 更勤快，是**给完成状态一个可读的位置**。

## 7 判据（形态无关 —— 这一节决定这份规范能不能跨项目用）

**下面的判据只问结构，不问词汇。** 任何项目、任何语言、任何文档组织方式都必须能过：

```
G-域 1 域表存在，且每一格非空（抓「模板抄了没填」）
G-域 2 域表里声明的文档路径，在仓库里真实存在（硬判据）
G-域 3 每个域都有「不管什么」（边界）
G-域 4 每个域都能回答「删掉它会怎样」
G-域 5 至少一条未知 / 未定，且写了「怎么验」
G-域 6 全文没有补丁段（原写…现改为…／补记／修订记录）
```

**反例（这些是形态，不许写成判据）**：

```
❌ 「必须有九个域」        —— 域的数量由问题决定
❌ 「必须有域表这一节」    —— 概念是「域被列清了」，标题叫什么随意
❌ 「必须写串/并/汇」      —— 概念是「域之间的依赖方向写了」，用词随意
❌ 「必须用 D1–D6 编号」   —— 概念是「六条纪律在」，编号是这套模板的偶然
```

**⇒ 判据里出现「这次项目的词汇」，它就只能对一个项目有效。**

---

## 8 例证（是例证，不是规范）

一个记忆库项目的域是这样**推**出来的，不是照抄九个：

```
困境：回忆时能交出「能解释这个词的东西」，而不是一条 id
推：要成立必须有 → ① 词怎么定 ② 东西怎么存 ③ 存的对不对能不能证
                  ④ 代码怎么分层 ⑤ 模块怎么接 ⑥ 具体怎么写
                  ⑦ 一次写入从字节到行 ⑧ 谁在用 ⑨ 怎么算过
```

**九个是推出来的结果。换个项目，推出来可能是五个、十四个，或者两个。**

**⇒ 抄「九」的人，抄到的是那次推导的下标，不是推导。**

## 9 自检

- [ ] 每个域都能回答「删掉它会怎样」，答不出的已并入别的域
- [ ] 每个域有：管什么（带反例）/ 不管什么 / 怎么算过
- [ ] 每个域都问过「这一层有词汇吗」，没词的已先造词
- [ ] 域之间的关系写了串 / 并 / 汇，串链无反向依赖
- [ ] 需求引导问过：有没有用「两个选项带代价」而不是开放题
- [ ] 用户说不清的地方，有 assumption 标注 + 行业依据（谁这么做 / 为什么 / 代价）
- [ ] 行业也空白的，写进未知项，且写了「怎么验」
- [ ] 全文无补丁段；改上游时已按串链反查了下游
- [ ] 状态表存在，「定稿」都有证据指针
- [ ] 判据里没有任何「本项目的词汇」
