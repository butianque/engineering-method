# R8 施工节奏：一片怎么跑完，才算跑完

> **这一份是从一次真实施工里抽出来的**（一个库、8 个功能片 + 7 个重构片、294 条测试、20 份开发日志）。
> 它不是「流程建议」，是**那 15 片里，凡是做对的地方共有的动作**；做错的地方，都缺其中一条。
>
> **一句话**：**一片的边界不是「功能做完」，是「两个流都被看见，并且注入能把它弄红」。**

---

## 1 一片的九个动作（顺序不许换）

```
① 定规范   先改文档（这一片的语义），再改代码
② 冻契约   签名 / 结构体 / 常量原样贴进任务书；子代理只许填函数体
③ 写探针   lead 自己写独立验收探针（不用子代理的测试）
④ 派活     按写域派；跨 crate 依赖串行 A → B，不许并行
⑤ 自己跑   lead 复跑子代理的测试，不看它自报的「全绿」
⑥ 双注入   子代理注入一次，lead 注入一次，红点不同才算交叉验证
⑦ 看两流   直接查库看行 / 直接读回看语义（不看包装）
⑧ 记账     开发日志六节（见 `templates/开发日志.md`）
⑨ 只改状态 D6：只改状态表那一行 + 证据指针，不重读已完成文档
```

**为什么①在最前**：这一片暴露的语义冲突，改代码时发现要返工两次；改文档时发现只返工一次。

## 2 十二条硬纪律（每条都有翻车记录）

### D-1 派活前先跑一次基线，把**真实数字**写进任务书

翻车记录：连续 **8 次**把基线数字写错（`217` vs `238`、`272` vs `276`、`276` vs `282`…），
原因都是「凭记忆 / 用上一次的数」。

```
正确动作：cargo test --workspace（或等价命令）→ 把总数与逐二进制数抄进任务书
附带一句：「别信我写的数，自己跑一遍再开工」
```

### D-2 数字与算术：写进断言前先算一遍

翻车记录：`m−p−1` 算错、`3+3>7` 当越界例子（其实 6≤7）、「6 原子」实际 9 个、「上下」码点序写反。
**连续 5 次同类错误，每次都是子代理兜住的。**

```
规则：凡任务书里出现数字，先写推导式，再填数。
      凡断言里出现计数，把算式写进注释，不只写结果。
```

### D-3 规范里「算法 + 样例」并存时，先用样例手推算法

翻车记录：写「`ctx = LCSuffix(左文) + cue`」，样例却是「早上/晚上 ⇒ ctx=吃」。
按字面算法应得 `ctx=上吃`、`fillers=[早,晚]` —— **算法推不出样例，就该推翻算法，不是修样例**。

### D-4 注入必须双方各做一次

```
子代理注入 → 红它的测试
lead 注入   → 红 lead 的探针
两边红点不同 = 交叉验证成立；只有一边红 = 那边有洞
```

### D-5 注入没红，先怀疑夹具，再怀疑实现

翻车记录：注入「`find_edge` 恒 None」没红 —— 因为反面方向才用它；
注入「`read` 兜底改 `?`」没红 —— 因为夹具里读从不失败。

```
规则：没红的第一反应是「这条断言覆盖不到这个分支」，不是「实现对了」。
```

### D-6 夹具必须同时触发被测的每一个分支

翻车记录：把 `dir` 改成永远 `after`，6 条探针全绿 —— 因为夹具里 `at` 是原子，只产生 after/before。

```
正确夹具：让 at 自己是一条边、又被另一条边当成员 ⇒ 三种方向同时出现。
```

### D-7 「测试全绿」不等于「主路径被覆盖」

翻车记录：`commit()`（落盘成功才换指针那一行）**从未被执行** —— 291 条测试里没有一条经过 HTTP handler。
把那一行注释掉，4 条测试照样全绿。

```
零覆盖检测法：把主路径那一行注释掉，看有几条红。一条都不红 = 零覆盖。
```

### D-8 行为判据抓不到「假重构」，必须有可机检的计数

翻车记录：把归一后的原语抄回调用方，8/8 快照全绿。只有计数能发现。

```
三类判据缺一不可：
  快照  → 对外字节没变
  wired → 内部确实调了原语
  计数  → 同一规则在源码里只剩 1 处（grep 可数）
```

### D-9 重构的通过凭证是「改前抓的快照」，不是「改后的期望值」

```
正确顺序：先打印并逐字符记进断言 → 确认它在改之前就是绿的 → 再动手
反例：改完再写断言 = 把「现在的样子」当成「应该的样子」
```

### D-10 测试条数改前改后必须相等（重构片）

```
276 → 276：同时阻止两件事 ——「测不过就删掉测试」和「断言太严就放宽」
条数变了必须解释差在哪（新增探针 / 删了壳对应的转发测试）
```

### D-11 判据与实现不一致时，只许两条路

```
A 改实现（判据是对的）
B 承认违反，把差距与代价写清（判据是对的，但这一版不做）
✗ 改判据迁就实现 —— 那是自欺，等于取消判据
```

### D-12 文档失真最难发现的是「当时为真的计划」

```
它读起来通顺、自洽，唯一毛病是描述的系统不存在。
只有机械对账能抓，而且必须是双向：
  代码 → 文档（文档没撒谎）
  文档 → 代码（文档说全了）
```

## 3 子代理：只执行，不验收（没有例外）

**用户的原话，就是这一节的全文**：

```
子代理只负责主代理给与的相关任务，不负责验收，
验收和规划由任务发出者验收，如有问题子代理也可如实上报。
就是这样。
```

**⇒ 分工是硬的，不是偏好**：

| 谁 | 干什么 | 不许干什么 |
|---|---|---|
| **任务发出者（lead）** | 规划这一片 / 冻契约 / 写独立探针 / **判定过不过** | 不许把「判定」外包出去 |
| **子代理** | 执行写域内的事 + 如实上报（含冲突、越界、做不到的） | **不许自判「这一片通过」**，不许改判据让它通过 |

**「纯搬运可以交给子代理自验」也是不允许的。** 理由：搬运恰恰是最容易悄悄改掉字节的地方
（错误文案、常量、指纹输出 —— 改了不影响编译、不影响逻辑，只影响调用方看到的字节）。
搬运片的通过凭证是 lead 的**逐字节快照**，不是子代理的「没改逻辑」。

### 3.1 上报不等于验收

**子代理必须上报，但上报的是「事实」，不是「结论」**：

```
✅ 可以报：「S4 里 5 成员、at=丙(p=2) 的 After 上界按冻结语义只有 2 条，与任务书的 3 条冲突，
           我按语义做了，请裁决」
✅ 可以报：「源码 0 处要改」+ 三条结构性理由 + 注入红点
✅ 可以报：「我够不到 store 的写域，这个洞我复现了但没修」（越界如实说）
✗ 不许报：「这一片通过」
✗ 不许报：「测试全绿，可以合了」
```

**⇒ 判据：报告里凡是「通过 / 完成 / 可以合了」这类结论，一律由 lead 下，不由子代理下。**

### 3.2 四条反直觉的事实

| # | 事实 | 后果 |
|---:|---|---|
| 1 | **它会替你兜住你写错的规范** | 它把冲突原文上报、说清两种口径的后果，而不是硬套。**这才是你要的交付** |
| 2 | **「源码 0 处要改」可以是有效交付** | 前提：结构性理由（为什么结构本身保证了）+ 注入能红的测试 |
| 3 | **它会越界做「临时注入」，允许但要留痕** | 事前说明 + 改前改后 SHA256 核对 + 交付时无痕迹 |
| 4 | **它会留中间产物** | 任务书要写「交付时清掉，只留可复现命令」 |

**⇒ lead 验收的三问**（对每份报告）：

```
1 它贴的输出，是不是它自己那条测试跑的？（不是「workspace 全绿」）
2 它说「0 处要改」时，有没有同时给出结构性理由 + 注入红点？
3 它新增的键 / 字段 / 分支，是我冻结契约里允许的吗？（多一个就是套壳的开始）
```

## 4 两个流怎么「看」

| 流 | 看什么 | 怎么看（不许看包装） |
|---|---|---|
| **数据流** | 行数 / 字段 / 位置 / 事务边界 | 直接连库查：`entities` 几行、`pos` 是 0,1,2 还是 1,2,3、指纹是拼接还是哈希 |
| **信息流** | 读回 / 落点 / 余量 / 分组 | 直接调端点看 JSON：`textAt` / `start..end` / `leftOff` / `exact` |

**反套壳判据（每片都查）**：

```
改库里一行（把 pos=1 的成员从「乙」改成「丁」）
⇒ 读回必须跟着变（甲丁丙），落点也必须跟着变
⇒ 仍读回原串 = 读法被存了或查表拼的 ⇒ 判不通过
```

## 5 记账：开发日志六节（固定）

```
一 改动了什么   层 / 文件 / 函数
二 得出了什么   可复算的数字：行数、读回、注入红点
三 架构长什么样  依赖图 + 每个包「不许做什么」
四 加了哪些文件  完整清单（要能映射到落位表）
五 做到了什么    逐条 ✅ / ⬜，未做的诚实标注
六 坑           现象 / 解 / 正确做法
```

**第 二 与 第 六 是这份日志存在的理由**；其余四项只是索引。
**不写过程叙事**（讨论、试错推演）—— 那些留在 git 与对话里。

---

## 6 一片结束时必须能回答的四句话

```
1 数据流：哪几张表、各几行、顺序对不对（贴实测）
2 信息流：消费者拿到什么、能不能直接用（贴 JSON）
3 反证：注入什么、红在哪条、还原后是否全绿
4 边界：这一片没做什么（明确写出来，否则下一片会以为它做了）
```

**答不出第 4 句 ⇒ 下一片必然重复劳动或漏做。**

## 7 自检

- [ ] 规范先改，代码后改（①）
- [ ] 契约冻结，子代理只填函数体（②）
- [ ] lead 有独立探针，且自己复跑过（③⑤）
- [ ] 跨 crate 依赖串行，没有并行撞 `unimplemented!()`（④）
- [ ] 双方各注入一次，红点不同（⑥）
- [ ] 两个流都看的是库与读回，不是测试名（⑦）
- [ ] 任务书里的数字是刚跑出来的，不是记忆里的（D-1）
- [ ] 主路径那一行注释掉后，确实有测试变红（D-7）
- [ ] 重构片：快照改前就绿、计数从 N 处降到 1 处、测试条数不变（D-8/D-9/D-10）
- [ ] 日志六节齐，第六节至少 1 条（⑧）
- [ ] 只改了状态表那一行（⑨）
