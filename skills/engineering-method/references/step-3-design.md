# 层一·三定：设计（`设计.md`）—— 转折点

> **到了这一步，才知道自己到底缺什么。**
>
> 前面三步（应然形态 / 规划 / 策划）都是在"想"。
> 设计是**第一次要把东西画出来**——一画，缺口就露出来了。

---

## 一、为什么必须两段，且必须按顺序签收

```
段一：系统设计 —— 部件之间怎么接（跨组件 / 跨仓库 / 跨进程）
        ↓ 必须人签收
段二：程序设计 —— 部件内部代码怎么长（模块内）
```

**不许反，也不许合并。**

| 如果先写段二 | 后果 |
|---|---|
| 先想"函数怎么写" | 每个函数都自洽，但**部件之间的契约没人定** |
| 定完再补段一 | 段二写的每个函数都要改，因为它按错的假设写的 |

**⇒ 签收是物理动作，不是仪式：**
**`.runs/signoff-system-design.md` 不存在 ⇒ `gate.sh` 拒绝进入段二。**

## 二、段一：系统设计

### 2.1 部件清单

| # | 部件 | 职责（一句话） | 属于哪个仓库/进程 |
|---|---|---|---|
| 1 | | | |

**判据：每个部件的职责能用一句话说完。说不完 = 它其实是两个部件。**

### 2.2 部件之间的契约 ★ 最容易做差的一节

| # | 从 | 到 | 交什么（**字段级**） | 失败时谁兜 |
|---|---|---|---|---|
| 1 | | | | |

**"字段级"的意思：**

```
❌ 「传用户信息过去」
✅ 「交 {id:int64, name:string, expireAt:RFC3339}；expireAt 为过去时间表示已过期」
```

**为什么必须到字段级**：不到字段级，"对得上"就是感觉，不是事实。

### 2.3 数据流 / 信息流（两个都要）

| 方向 | 交出的是什么 | 消费者能推出什么 |
|---|---|---|
| | | |

**这一列（消费者能推出什么）是判据：**

```
❌ 交出 {"target": 0}            → 消费者推不出任何东西
✅ 交出 {"target": 0, "text": "是红"}  → 消费者知道"这个概念没物化，读法是《是红》"
```

**⇒ 只要"消费者推不出任何东西"，这条就是只交了数据流。**

### 2.4 外部依赖与边界

| 依赖 | 版本 / 接口 | 挂了会怎样 | 有兜底吗 |
|---|---|---|---|

### 2.5 签收

```
签收人：____
时间：____
明确接受的取舍：____
```

**落在 `.runs/signoff-system-design.md`。**

**"明确接受的取舍"这一栏必须有内容。**
**空着 = 签收者没看懂 = 不许开段二。**

## 三、段二：程序设计

### 3.1 契约 → 兑现 映射表 ★ 这是绝大多数设计缺的东西

| # | 系统设计的契约 | 谁来兑现（文件:符号） | 怎么验 |
|---|---|---|---|
| 1 | 接口 A 返回 `{id, name, expireAt}` | `pkg/x.go:GetUser` | `grep -q 'expireAt' pkg/x.go` |
| 2 | 配置项 B 变更立即生效 | `pkg/y.go:onConfigChange` | `验收.sh --case reload` |

**为什么必须有这张表：**

```
没有它 ⇒ 可以写出两份都漂亮、但互不对应的设计
        段一承诺了 8 个契约，段二实现了 6 个，没人发现少了 2 个
有它   ⇒ 每个契约必须指向一个兑现点，指不出就是漏了
```

**`[gate]` 本表无空行。**

### 3.2 模块边界

| 模块 | 能碰什么 | 绝不能碰什么 |
|---|---|---|

**"绝不能碰"这一列比"能碰"更重要** —— 它是防越界的判据。

### 3.3 状态与并发

| 状态 | 存在哪 | 谁写 | 并发怎么处理 |
|---|---|---|---|

**并发那一列写"不用考虑"也行，但要写。** 不写 = 没想到。

### 3.4 失败路径

| 可能失败 | 怎么发现 | 怎么传上去 | **消费者看到什么** |
|---|---|---|---|
| | | | |

**最后一列必须是人能看懂的话：**

```
❌ 500
✅ 「登录已过期，请重新登录」
```

### 3.5 本设计故意不做的

| # | 不做 | 理由 |
|---|---|---|

**这一节不是可选的。** 没有"不做"，边界就是无限的。

## 四、设计做完，缺口在哪（这一步的输出就是「认知补给」的输入）

**必须列出来：**

| # | 我缺什么认知 | 该补给的方式 |
|---|---|---|
| 1 | | 读仓 / 借鉴成品 / 搜论文 / 跨学科 |

**⇒ 这些缺口不是"以后再说"，是下一步的输入。**
**补给完 → 沉淀进 `范畴表.md`（划界）→ 回来改这份设计。**

**这一步是整条链的枢纽**：

```
前面（0–2）：在已有范畴内推理
这里（3）：  第一次撞到"我的范畴不够用"
后面（5–6）：补上不够的那块
```

## 五、常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 跳过段一直接写段二 | 每个函数都自洽，接起来不通 | 先补段一，再返工段二 |
| 契约不到字段级 | "对得上"靠感觉 | 写到 `{a:int, b:string}` |
| 映射表留空 | 承诺了 N 个契约，兑现了 M 个 | 每个契约必须指到文件:符号 |
| 只交坐标 | 消费者拿到 id 不知道啥意思 | 加人能读的字段 |
| 空着"不做"清单 | 边界无限，永远做不完 | 强制 ≥3 条 |
| 没列缺口 | 认知补给无从开始 | 强制列 ≥1 条 |
