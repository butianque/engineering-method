# 层一：应然形态、切片表、策划

> 这三件事的共同点：**都在纸上，都还没碰代码。**
> 它们回答三个不同的问题，不许混：
>
> | 位置 | 问题 | 答错的症状 |
> |---|---|---|
> | **层一·域** | **它应该长什么样，我才能完成它？** | 写成"功能清单" |
> | **层一·切片表** | **分几片、每片边界在哪？** | 写成排期表 |
> | **层一·策划** | **选哪条路、代价多少？** | 只有一个方案 |
>
> **域的来源与推导不在这里**（唯一权威：`r6-project-charter.md`）；**分片形态不在这里**（唯一权威：`r7-slice-board.md`）。
> 本文只负责这三件事的「问法」与「答错的症状」。

---

# 层一·域：应然形态（`立项书.md`）

## 1 这一问为什么是这个问法

**不是"你要做什么"，是"它应该长什么样"。**

差别：

```
"你要做什么"      → 用户说他想要的东西 → AI 照着做 → 做出来是个零件
"它应该长什么样"  → 用户说他的困境     → 一起推出形态 → 形态里自然包含零件和接线
```

**例子**：

| 用户说 | "要做什么"的回答 | "应该长什么样"的回答 |
|---|---|---|
| 「加个登录」 | 写一个登录接口 | **一个换设备后仍被认作同一人的状态** → 需要会话、令牌、过期判定、设备识别、失败路径 |
| 「加个缓存」 | 接一个 Redis | **同一个查询在 N 秒内不重复打上游** → 需要 key 设计、失效策略、穿透保护、一致性 |

**⇒ 同一句话，两种回答，产出量差 5–10 倍。**

## 2 清单不在这里定义

**立项书该填哪几节，唯一权威是 `templates/立项书.md`；域从哪来，唯一权威是 `r6-project-charter.md`。**

这一节只说一件事：**为什么第 3 项（可观测的成功判据）是唯一有牙齿的一项。**

## 3 可观测判据是整份立项里唯一有牙齿的一项

**判据：能不能被一条命令验出来？**

| ❌ 验不出 | ✅ 验得出 |
|---|---|
| 完成度 90% | 重启后数据还在 |
| 代码写好了 | `curl /health` 返回 200 |
| 体验流畅 | 首屏 1s 内，用 Lighthouse 测 |
| 基本没 bug | 连续跑 100 次，0 次失败 |

**⇒ 验不出的判据，等于没有判据。它会退化成"我觉得好了"。**

## 4 不做清单为什么必须有

**"不做清单"是范畴的物理形态。**

没有它：
```
任何东西都能被说成"完成了" —— 因为"该做的"边界是无限的
```

有它：
```
"这次不做多租户" → 有人提多租户，答案明确：不在范围内
```

## 5 未知项为什么必须填

**"未知项"是给下一步的输入清单。**

```
留空 = 我以为我都知道了 = 那通常是盲区所在
写"不知道 X，打算用 Y 方法验证" = 有下一步
```

# 层一·切片表：规划（`规划.md`）

## 6.1 规划不是排期

```
❌ 排期：第 1 周做 A，第 2 周做 B（按时间切）
✅ 规划：分几个阶段，每阶段的退出判据是什么（按可交付切）
```

**时间估算永远不准，退出判据永远有效。**

## 6.2 阶段必须垂直切片

```
❌ 水平分层：
  阶段 1：所有 model
  阶段 2：所有 service
  阶段 3：所有 API
  ⇒ 阶段 1、2 结束时，什么都验证不了

✅ 垂直切片：
  阶段 1：一个接口从路由到存储全通（只支持一种情况）
  阶段 2：加第二种情况
  阶段 3：加并发和失败路径
  ⇒ 每阶段结束都能从外面打一次
```

**判据：每个阶段结束时，能跑一次端到端。**

## 6.3 退出判据的三种合法形式

| 形式 | 例 | 适用 |
|---|---|---|
| 命令退出码 | `bash 验收.sh --case <阶段>` | 有可测产物 |
| 一次可观测操作 | 「从入口打一次，200 且体里有 X」 | 手动可验 |
| 人工签收 + 记录 | `.runs/signoff-<阶段>.md` | 纯决策阶段 |

**写不出退出判据 ⇒ 它不是阶段，是同一步的两半。合并它。**

## 6.4 禁止的依赖

```
❌ 阶段 N+1 依赖阶段 N 才能验证
   ⇒ 说明 N 没有独立判据
```

**这个禁止是有实证的**：某套 17 阶段的流程，后半段全部依赖前半段才能验，
结果跑到一半就没人知道"现在到底对不对"。

## 6.5 人判断点（≤3 个）

**必须人签的典型位置：**

| 位置 | 为什么 |
|---|---|
| 系统设计 → 程序设计之间 | 结构错了，后面每行代码都在错的结构上 |
| 方案选型（策划的 A/B） | 代价判断需要业务上下文 |
| 不可逆操作前 | 删数据 / 改线上配置 / 发版 |

**⇒ 24 小时自动化 ≠ 没有人。是人不进日常回路，只守这几个出口。**

# 层一·策划：策划（`策划.md`）

## 7.1 没有备选方案 = 没做策划

```
❌ 只有方案 A + 一堆理由说 A 好
   ⇒ 这是"把已经决定的事写成文档"

✅ 方案 A 和 B 各有一段，各自说清代价和风险
   ⇒ 这才能叫策划
```

## 7.2 每个方案必须回答四个问题

| 问题 | 为什么 |
|---|---|
| 是什么（一句话） | 防止含糊 |
| 代价（工时/复杂度/新依赖/运维负担） | 备选就是用来比代价的 |
| 风险 | 会不会炸 |
| **什么情况下它是错的** | 这条最难写，但最有用 |

## 7.3 "什么情况下它是错的"怎么写

```
❌ 「基本没问题」
❌ 「风险可控」
✅ 「选 A，因为运维只需一个进程；如果并发超过 500/s，A 会成瓶颈，那时该切 B」
```

**判据：写出的条件必须是**可观测的**（并发数、数据量、团队人数），
不是"如果未来需求变了"这种没法判的。**

## 7.4 回滚方案必须有验证

| 项 | 要求 |
|---|---|
| 怎么退 | 具体命令/操作 |
| 退的代价 | 丢多少数据、停多久 |
| **怎么验退干净了** | 一条命令或一次检查 |

**"应该没事"不算。**

## 7.5 策划和规划的关系

```
规划：分几步（纵向，阶段）
策划：选哪条路（横向，方案）

一个阶段里可能有一个策划（这一步用 A 方案还是 B 方案）
一个策划也可能跨多个阶段
```

**⇒ 两者不冲突，但不要混在一个文档里。**

## 8 自检

**层一·域**
- [ ] 核心问题是"如何…"，不是名词短语
- [ ] 成功判据每条都能被命令/操作验出来
- [ ] 不做清单 ≥3 条
- [ ] 未知项至少 1 条

**层一·切片表**
- [ ] 每阶段有退出判据，无空阶段
- [ ] 每阶段是垂直切片
- [ ] 没有"阶段 N+1 依赖 N 才能验证"
- [ ] 人判断点 ≤3 个
- [ ] 阶段数 ≤7

**层一·策划**
- [ ] 备选 ≥2
- [ ] 每个都有"什么情况下它是错的"
- [ ] 选择理由可反驳
- [ ] 回滚方案有验证方法
