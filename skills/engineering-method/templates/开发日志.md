# 开发日志（一片一份）

> **命名**：`<版本>/开发日志/<YYYYMMDD-HHMM>-<名称>.md`（用**开工**时间，便于按时间线排）。
> **只写**：改了什么 / 得出什么数字 / 架构 / 新文件 / 做到什么 / 坑。
> **不写**：讨论过程、试错推演、决心表态 —— 那些留在 git 与对话里。
>
> 依据：`references/r8-slice-rhythm.md` §5。

---

## 一、改动了什么

| 层 / 文件 | 做了什么 |
|---|---|
| | |

**要点**：写到函数级。让三个月后的自己能定位「这行是谁加的、为什么」。

---

## 二、得出了什么（可复算的数字）

**数据流**：

```
表 A   N 行，kind = …
表 B   N 行，pos = 0,1,2
表 C   N 行
写前 / 写后  四元组：(…) → (…)   ← 只读片必须逐项相等
```

**信息流**：

```json
{ "…": "实际端点返回（截关键字段）" }
```

**反证**：

| 注入 | 红在哪条 | 还原后 |
|---|---|---|
| | | |

**要点**：第二节是这份日志存在的第一理由。**没有数字的「完成了」不算完成。**

---

## 三、架构长什么样

```
<包依赖图，谁不许 import 谁>

包 / 模块        行数      pub 数      不许做什么
```

**要点**：写「不许做什么」，因为那才是下次会被破坏的东西。

---

## 四、加了哪些文件

| 文件 | 干什么 | 映射到落位表哪一行 |
|---|---|---|
| | | |

**要点**：映射不到的，说明落位表要补 —— 不许裸放（G6）。

---

## 五、做到了什么

```
✅ …（有证据指向第二节的哪条数字）
✅ …
⬜ …（未做，为什么）
```

**要点**：未做的必须写出来，否则下一片会以为它做了。

---

## 六、坑

| # | 现象 | 解 | 正确做法 |
|---:|---|---|---|
| 1 | | | |

**要点**：这一节是这份日志存在的第二理由。**至少写一条**，写不出说明这一片没有新事实（螺旋无效）。
模板对照：数字没算就写断言 / 注入没红就怀疑实现（其实夹具覆盖不到）/ 基线数字凭记忆 / 主路径零覆盖 / 文件名是另一个的子串。

---

## 自检

- [ ] 文件名用开工时间，`YYYYMMDD-HHMM-名称.md`
- [ ] 六节齐
- [ ] 第二节有可复算的数字（行数 / 读回 / 红点），不是「已验证」
- [ ] 第三节写了「不许做什么」
- [ ] 第四节每个文件都能映射到落位表
- [ ] 第五节未做的已标 ⬜
- [ ] 第六节 ≥1 条，且是「现象 / 解 / 正确做法」三段
- [ ] 全文没有过程叙事
