# 立项书（基准，不是介绍）

> **两个问题一起答**：它应该长什么样，我才能完成它（§1–§6）；后面几十份文档凭什么不许互相打架（§7–§11）。
>
> **这份文件是基准**：下游文档每一条声明，都要能被它逐行判「是 / 否」。
> **填不满就重做**：允许写「不知道」，**不许留空**——留空是最坏的一种谎。
>
> 详细判据：`references/steps-0-2.md`（§1–§6）、`references/r6-project-charter.md`（§7–§11）。

---

## §0 一句话

**<系统是什么，一句话说完，含最强的那条约束。>**

> 判据：删掉那条约束，这个句子会变成另一个系统 ⇒ 这才是最强约束。
> ❌「一个记忆库」　✅「只存符号与符号集；不判断、不语义、不量化；状态归调用方」

---

## §1 核心问题

**一句话**：如何……

> ❌「实现一个登录功能」
> ✅「如何让一个用户在换设备后仍被认作同一个人」

**为什么这不是标题**：标题可以是名词（「登录」），核心问题必须是一个**待解的困境**。

---

## §2 消费者是谁

| 谁 | 怎么用它 | 它失败时会怎样 |
|---|---|---|
| | | |

**至少要有一个真实的人或系统。** 写「用户」不合格——写清是哪个用户、在什么场景。

## §3 外部可观测的成功判据

| # | 判据 | 怎么观测 |
|---:|---|---|
| 1 | | |

> ❌「完成度 90%」　❌「代码写好了」
> ✅「重启后数据还在」　✅「并发 10 个请求，状态码全 200 且计数等于 10」

## §7 域表（立项的脊柱）

| # | 域 | 回答什么 | 入口文档 | 现状 |
|---:|---|---|---|---|
| 1 | 数学 / 认知范畴 | 词怎么定、边界在哪、什么不属于本系统；要哪几件数学；语言怎么选 | | 草案 |
| 2 | 架构 | 系统长什么样、谁调谁 | | 草案 |
| 3 | 形式化证明 | 哪些命题被机器证过 | | 未开始 |
| 4 | 工程 \ 架构 | 代码怎么分层、依赖方向 | | 草案 |
| 5 | 框架 | 模块、接口、目录、装配点 | | 草案 |
| 6 | 工程片段细则 | 事务 / 锁 / 幂等 / 编码 / 测试的具体写法 | | 草案 |
| 7 | 数据流 \ API | 字节怎么变成行；端点参数 / 响应 / 错误码 | | 草案 |
| 8 | 消费者 / 信息流 | 谁在用、时机、频率、方式、失败怎么办 | | 草案 |
| 9 | 工程判据 | 怎么算过；红一条不许合 | | 草案 |

**每域必须交三件套**：回答什么 / 交付什么（具体到文件）/ 判据（怎么算过）。
**只许把「本版不做」的域移出表并写进 §4；不许把两域并成一个文档。**

---

## §8 依赖顺序

```
【串】设计链
  域1 → 域2 → 域4 → 域5 → 域6

【并】可并行的两条
  域3（证明）  ∥  域7（数据流 / API）

【汇】依赖上面全部
  域8（消费者）依赖域7；域9（判据）依赖全部
```

**规则：串链上每一环只依赖它前面那环，不反向依赖。反向依赖 = 环形 = 谁也改不了。**

---

## §9 落位表（文档与代码分家）

```
<项目>/
├── docs/                     ← 文档全部按域分目录
│   ├── 00-立项书.md           ← 本文（基准）
│   ├── 90-文档宪法.md         ← 纪律（改法 / 编号 / 唯一权威）
│   └── <NN-域>/              ← 每个域一个目录，一个入口文档
└── <版本>/                   ← 只放代码与运行物，不放文档
```

**判据：每个新文件都能映射到本表某一行；映射不上就补表，不许裸放。**

## §10 裁决点

| # | 裁决什么 | 已定 / 未定 | 依据（判据编号） | 它决定哪些下游文档 |
|---:|---|---|---|---|
| 1 | | | | |

**要求**：未定项写「它决定哪些下游文档的写法」——这样它不阻塞前面，也不会被忘掉。
**已定项写依据（判据编号），不写「综合考虑」。**
